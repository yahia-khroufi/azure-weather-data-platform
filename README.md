# Azure Weather Data Platform

Cloud data-engineering project that ingests current weather observations from
OpenWeather into Azure Data Lake Storage Gen2. The first milestone deliberately
stops at the RAW layer; Databricks, Azure SQL, and Power BI come later.

## Current scope

```text
OpenWeather API
      |
Azure Data Factory (system-assigned managed identity)
      |-- reads secret --> Azure Key Vault
      `-- writes RAW ----> ADLS Gen2
```

The repository currently provides:

- a local OpenWeather client for development and API-contract exploration;
- reusable configuration and initial data-quality rules;
- Terraform for Resource Group, ADLS Gen2, Key Vault, ADF, and RBAC;
- unit tests and a non-deploying CI workflow.

ADF calls OpenWeather directly in production. `src/ingestion/openweather_client.py`
is not part of that production request path.

## Project structure

```text
src/                    Local Python client, utilities, and quality rules
config/cities.json      Versioned, non-secret city configuration
infrastructure/terraform Azure foundation for MVP 1
adf/                    ADF Git-integration root (artifacts generated by ADF Studio)
databricks/             Reserved for MVP 2 transformations
sql/                    Reserved for the later analytics phase
tests/                  Unit and integration tests
docs/                   Architecture and operations documentation
```

## Local setup

Python 3.12 is recommended.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Set `OPENWEATHER_API_KEY` in `.env`, then fetch the cities configured in
`config/cities.json`:

```powershell
python -m src.ingestion.openweather_client
```

The command prints the original JSON response for every configured city. `.env`
is ignored by Git.

Run local checks:

```powershell
ruff check .
pytest -q
```

## Provision the Azure foundation

Prerequisites: Azure CLI, Terraform 1.7 or later, an Azure subscription, and
permissions to create resources and role assignments.

```powershell
az login
az account show
Set-Location infrastructure/terraform
Copy-Item terraform.tfvars.example terraform.tfvars
```

Edit `terraform.tfvars`: set the subscription ID and replace `unique_suffix`
with 3–8 lowercase letters/digits unique to you. Do not put the OpenWeather key
in Terraform.

```powershell
terraform init
terraform fmt -check -recursive
terraform validate
terraform plan -out main.tfplan
terraform apply main.tfplan
```

Terraform creates one `datalake` filesystem. The `raw/`, `bronze/`, `silver/`,
`gold/`, and `config/` paths are created when data is written.

## Secret and ADF MVP 1

After provisioning, add a Key Vault secret named `openweather-api-key` manually.
The ADF managed identity already receives `Key Vault Secrets User` on the vault
and `Storage Blob Data Contributor` on the storage account.

Next, connect ADF Studio to this repository with `/adf` as its root. Let ADF
Studio generate its JSON artifacts. Build and debug this flow before adding any
Databricks resources:

```text
Lookup cities.json -> Read Key Vault secret -> ForEach city
                   -> Copy OpenWeather JSON -> ADLS datalake/raw/weather/...
```

Only after a successful RAW write should the hourly trigger be enabled.

## Security

- Local secrets live only in ignored `.env` files.
- Production secrets live in Key Vault, never in Git or Terraform variables.
- ADF uses a system-assigned managed identity and least-purpose RBAC roles.
- Storage public blob access is disabled and TLS 1.2 is required.

## Roadmap

1. MVP 1: OpenWeather → ADF → ADLS RAW, then an hourly trigger.
2. MVP 2: Databricks and RAW → Bronze → Silver → Gold.
3. Analytics: Azure SQL star schema and Power BI.
4. Industrialization: integration tests, remote Terraform state, CD, monitoring,
   alerts, and full architecture documentation.
